# Full original-product features and navigation — implementation plan

Date: 2026-10-17. Status: proposed implementation specification, not a completion claim.

Execution procedure: [step-by-step runbook](full-product-execution-runbook.md), including task order, ownership, review cycle and blocker handling.

## 1. Outcome and definition of 100%

Contractor must expose every supported original-product workflow through its desktop navigation, with real authorized services, persistent records, correct domain rules, and usable list/detail/edit/review/export flows. Preserve the current three-level Contractor shell and the user's explicit editor decisions. A tab, populated sample table, package test, or launch button alone is not a completed feature.

This document supersedes the completion claims in the delivery log of `frontend-product-integration-plan.md` for current product-readiness assessment. It does not erase historical engine work or merged milestone records. The new closure work is registered in [M13](milestones/M13-product-feature-navigation-closure.md); the [coverage appendix](../frontend/full-product-coverage.md) assigns all 64 currently inventoried routes and all 41 M00 workflows to work packets. Those are starting inventories, not a proven final denominator.

Completion requires three independently reported measures:

- **Navigation:** every source route, tab, detail page, alias, print/designer route and role-specific destination resolves correctly and has navigation evidence.
- **Behavior:** every inventoried user action has working validation, permissions, persistence/read-back, cancellation/error behavior and service-backed evidence.
- **Release:** every required platform and editor capability has its own executed compatibility, upgrade and recovery evidence.

Do not average these into a misleading percentage. Report verified/total, partial, blocked and unverified separately. An alias may share implementation but still needs a navigation check. A source feature explicitly changed by the user is marked `replaced-by-user-decision`, with equivalent outcome evidence; it is never silently deleted from the denominator. Partial original features remain identified as partial; 100% parity does not mean inventing all features that the old product never completed.

## 3. Decisions carried forward

1. **IPC starts in Contractor:** choose project/contract, IPC number and period, create a durable IPC identity and a separate workbook, then open full GridCraft. No pre-existing project workbook is required to create the first IPC.
2. **IPC workbook/payment editing is GridCraft-only.** Contractor displays validated payment data and sync evidence. Do not reintroduce quantity, deduction, total, certification or paid-state editing in this surface. Any original approval/payment outcomes are retained as read-only projections or handled in the existing separately authorized workflow/finance surface; never infer an approval from a workbook save.
3. **Only Summary of Payment is required for IPC payment ingestion.** Bill, price-adjustment summary/calculation and supporting sheets remain in the workbook. Do not create duplicate app calculation models for them. The supplied IPC-9 workbook is populated reference material, not a blank production template; it does not contain the requested Abstract of Quantity format.
4. Reuse full GridCraft and TruePPM, and qualified ArtCraft integrations where previously adopted. A custom preview or in-memory adapter does not substitute for the full editor. No speculative upstream fork or invented editor API.
5. Preserve authoritative construction/accounting/authorization rules in existing services. Financial values remain exact decimals; date-only periods retain their meaning and BS/AD conversion policy.
6. Keep the present consolidated **BOQ, VO & IPC** module; map original separate routes to its tabs. Do not silently move BOQ back under Planning because an old manifest did so.
7. Preserve original supported overview/analytics behavior last. New analytical features beyond original scope remain deferred. Completing existing dashboard parity is distinct from starting a new analytics product.
8. Desktop is the immediate product target. Qualify macOS first; preserve the native/web shared architecture and publish separate Windows/Linux/web status. Do not claim mobile/editor parity without the existing platform matrix's required evidence.

## 4. Complete navigation model

Use one registry in `packages/construction_application`, consumed by the shell, route parser, menus, breadcrumbs, command palette/search, notifications and tests. A route contains stable ID, scope, module/view/entity IDs, capability, permitted query state and factory binding. Display labels never drive screen selection.

### Organisation workspace

| L1 module | Required destinations and actions |
|---|---|
| Desk | Existing overview, activity feed, My Tasks/approvals, notifications; links open the correct scoped record |
| Projects | Portfolio, search/filter, create, details, membership/access, open project, archive/restore under original rules |
| Materials | Central material/resource catalog, vendors, rate/profile libraries and presets; project use is explicitly scoped |
| Finance | Accounts/parties, cash/bank, original company/JV reports and guarantees where supported; no project data leakage |
| HR | Team/person directory, user versus worker identity, employment/assignments, roles and handover |

L3 views must come from inspected source components and domain workflows, not invented label lists. The appendix preserves every known path, including utility/auth and print-only routes. Original mobile-only journeys must be cross-referenced in M13-T01 even if absent from the 64 desktop-route seed.

### Navigation acceptance contract

- Organisation/project switching changes context, data and capability projection together. Return-to-portfolio and per-project last location work; inaccessible views fall back to a documented allowed route.
- Direct links, native reopen, browser refresh/back/forward and app back navigation restore the correct entity, selected tabs and shareable filters. Unknown/deleted/forbidden links have distinct recovery states.
- List → detail → edit/review → return retains pagination/filter/scroll where appropriate. Cancel does not mutate. Dirty forms resolve save/discard/cancel and editor work is not silently lost.
- Expanded/compact/hidden sidebar, user menu, sign out, original module reordering, light/dark/system theme, notifications and keyboard shortcuts work and persist per user.
- Parent tabs remain correctly selected for nested details/designers. A notification or cross-module link uses the same route registry; old route aliases cannot create a second data authority.
- Search, filters, sort, pagination, selection, bulk actions, column preferences, export, fullscreen and split view are implemented wherever the original supports them. Controls without a meaningful action do not appear as working controls.
- Desktop keyboard/focus and responsive layouts are verified at 1440×900, 1024×768 and narrow widths; Nepali text/IME and currency/date formats remain readable.

## 5. Architecture and implementation rules

### Composition and data

Keep `prototype/construction_client` as the product root during this work. Extract the real identity, authorized transport, mount, outbox and attachment services from the existing connected host into the shared composition root; do not create a second sync stack. Wire server configuration, signed-out/restoring/revoked/error states, selected organisation/project and all workflow stores explicitly.

Every repository call carries account + organisation + project (where applicable) and a scope generation. Reject late responses after a switch. Cache keys and durable stores are scoped; financial permissions come from the server. Missing configuration produces an actionable setup state, not a silently authenticated demo. Explicit development entry points may retain fixtures.

Each action binding records its actual query/command, DTO version, permissions, lifecycle, pagination, cache invalidation/change-feed event and offline policy. Offline policy is classified per action: cached read, durable offline command, or online-only authoritative transition. Reuse idempotency keys, expected versions, receipts, attachment dependency ordering and definitive-rejection handling. Clearly distinguish saved locally, awaiting sync, accepted by server and backed up.

Split `workspace_shell.dart` into navigation chrome and module factories/controllers. Finance, HR, equipment and other domain state belongs outside the shell. Existing field stores, BOQ services, scheduling, takeoff and document primitives are reused after auditing persistence and service bindings. Do not implement financial formulas inside dialog callbacks.

### IPC durable integration

Creation must reserve IPC identity/number durably, create a workbook without replacing an existing file, commit its link and recover from interruptions between file and database operations. Define whether contract-local numbering is needed from authoritative rules; do not assume project-only uniqueness is correct for all contracts. Detect duplicate/repeated requests, concurrent processes, disk-full and orphan files. A failed GridCraft launch must leave a recoverable IPC that can reopen.

Use a versioned blank template verified against the fixed Summary of Payment contract. Preserve the supplied reference's supporting layouts without treating its IPC-9 financial values as defaults. Prove layout/identity requirements before any automated cell population; app creation metadata must not become an IPC amount editor.

Processing path:

`GridCraft saved file → ordered save observation → stable immutable snapshot/hash → identity/schema checks → calculation freshness proof → exact-decimal summary validation → transactional accepted revision → read-only Contractor view`

Watch the parent directory to survive rename-based saves; debounce and check stability, reconcile on startup/focus and periodically to cover missed events. Allocate observation order before asynchronous reads; older captures cannot replace newer ones. Use retry backoff with terminal errors, crash recovery and bounded retention. A change in path/identity requires reconciliation, not guessing another workbook belongs to this IPC.

Keep the last accepted revision visible with its timestamp, source hash and stale/error status. Blank, explicit zero, formula error and missing dependency are different states. A cached number alone is not calculation freshness proof. Snapshot/formula freshness evidence must refer to the same exact bytes. Preserve immutable issued/certified revisions; later workbook changes cannot rewrite them. Server publication, if required by the original workflow, has a separate idempotent acceptance receipt and must not be implied by local validation.

GridCraft qualification uses a disposable representative workbook: supporting formulas/external dependencies, images/shapes, formatting, saved values and reopen. Prior image loss and formula-cache anomalies must be resolved or explicitly bounded by an accepted template capability contract before publication. No unsupported promise of universal Excel compatibility.

### Editors and documents

For GridCraft/TruePPM/CADCraft/PdfCraft/WordCraft/DeckCraft record the actual artifact/version, launch/control API, document identity, save-complete signal, failure behavior, supported file features and update rollback. Run the actual application; synthetic host tests supplement rather than replace this evidence. Link drawing revisions and measurements to BOQ quantities with provenance. Validate produced PDF/XLSX/DOCX/PPTX files with independent readers; XML fragments or export descriptors are not complete files.

## 7. Evidence and release gates

Each route/action record includes source hash/commit and file/component, source behavior, target route/controller, API/command, permission, offline policy, platform, implementation status, acceptance scenario, test artifact and unresolved issue. States: inventoried → specified → implemented → service-verified → UI-verified → release-verified. Blocked items retain their last achieved state and blocking dependency.

Required evidence per feature:

- Actual list/detail/create/update and every source-supported transition/export; fresh session and restart read-back.
- Empty/loading/error/retry, cancellation, denied role, revoked access, wrong tenant/project, stale version and duplicate submission.
- Offline/reconnect/restart for offline-capable commands; explicit online requirement for others.
- Exact financial results against authoritative fixtures, immutable approved records and audit/change-feed effects.
- Same dataset/user/viewport side-by-side comparison of original and Contractor; table columns/actions, dialogs, visual hierarchy, keyboard/focus and responsive behavior.

Required cross-module journeys:

1. Project → contract/BOQ → approved VO → IPC workbook creation → GridCraft save → validated read-only summary → separately authorized finance record; no duplicate posting on retry.
2. Requisition → approval → PO → receipt → stock → issue/transfer → supplier payable; cancellation/reversal preserves audit.
3. Person → assignment → offline attendance → accepted payroll → project cost → journal; identity and allocation remain consistent.
4. Drawing revision → calibrated takeoff → BOQ quantity → new drawing revision → affected measurement review.
5. Daily report/photos → review → schedule progress/look-ahead → issued progress report; restart and lost acknowledgment do not duplicate records.
6. Equipment/rental/fuel and subcontract measurement → verified cost/bill → accounting; permissions and period locks hold.
7. Organisation/project/account switch during queued work or editor save → no cross-scope data, wrong-project publication or unauthorized mutation.

Run focused unit/widget tests, real-store/service integration tests, actual editor fixtures and UI acceptance. Use existing platform/performance budgets and record dataset/hardware; measure scrolling, initial load, imports and sync responsiveness. IPC's small supported fixture target is visible summary within five seconds after an observable completed save; larger workbooks get measured budgets, not a universal promise.

The current environment previously blocked Flutter's shared SDK cache/lock and telemetry writes. Establish a writable permitted toolchain/CI runner before test-dependent closure. A blocked test is not passed. Analyze/build success is not an installer, editor or connected-workflow test.

Final release gate requires zero unexplained routes/actions, zero live sample identities/amounts, no generic fallback screens, all required acceptance evidence, verified migrations/backup/restore/upgrade and a rollback path. No unresolved data-loss, wrong-scope, financial correctness or permission defect can be waived by a cosmetic parity score. Platform limitations remain visible. Build/install on each claimed platform; do not infer Windows/Linux/web behavior from macOS.

## 8. First execution packet

Start with T01, then T02/T03/T04 and shell T05. The first demonstrable vertical is real sign-in → real project selection → daily report save/restart/sync → detail read-back. In parallel only when separately authorized, qualify GridCraft with disposable copies. Then complete Contractor IPC creation and the saved-summary path on the same scoped foundation.

Planning deliverables in this change are local documentation only. Implementation, production data changes, deployment and upstream editor changes are not performed by this plan. The existing protocol's one-task/one-PR and owner gate process remains the implementation delivery mechanism; refine broad downstream packets before coding them, keeping the master register as the single backlog.
