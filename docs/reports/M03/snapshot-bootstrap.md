- **Milestone:** M03 (Native identity, repositories and sync engine)

- **Evidence sources:** platform plan v3 §5.3 (snapshot bootstrap, cursors, tombstones), §5.2 (local durability), [M03-T03 outbox report](sqlite-outbox-recovery.md) (pending-work preservation input), [M03-T04 feed report](sync-feed-pilot.md) (watermark continuation, ADR-0011 checkpoint discipline)

## 1. Purpose and scope

This task builds the bootstrap half of the M03 sync engine: initialize a device to a consistent server state and continue from the feed without losing pending local work. The package (`@contractor/native-snapshot`, zero runtime dependencies) carries both sides, mirroring the M03-T04 two-sides-one-package pattern: a server `SnapshotService` that materializes bounded, deterministic snapshots anchored to a feed watermark, and a client `SnapshotApplier` that applies pages in one transaction with a durable cursor, duplicate-page immunity, tombstone handling, and a completion reconcile that preserves pending local work. Like the T03/T04 packages it defines a structural `SqlDriver` port matching `node:sqlite`'s `DatabaseSync`, so the evidence below runs against **real SQLite databases** in CI itself — no mocks as durability proof.

The package ships **no domain schema**. On the server, rows and scope tombstones arrive through an injected `SnapshotSource` port called *inside* the open transaction; on the client, entity applies go through an injected `SnapshotEntityApplier` port and pending-work protection through a `PendingWorkProbe` port the mount wires to the M03-T03 outbox (the package never imports it — zero-dep isolation preserved). Both class surfaces are pinned by test to exactly their four public methods — no domain writers on either side.

## 2. One consistent state: materialized snapshots with a watermark

`openSnapshot` reads the watermark and materializes all rows and tombstones inside ONE `BEGIN IMMEDIATE` transaction; the materialized object set is immutable afterwards. This gives the acceptance line directly: snapshot data and its watermark represent one consistent state, and concurrent writes during bootstrap never change what the pages contain (tested: a row added, a row mutated, and a tombstone registered after open are all invisible to every page). Materialization failure is transactional too — a source that throws mid-open or a set exceeding the explicit `maxObjects` bound leaves neither manifest nor objects behind (typed `misconfigured`, tested). The watermark is the feed cursor the client continues from; in the repo evidence the port is called exactly once inside the open transaction (counter-pinned), and the same-database mount can make it exactly consistent by construction. A mount that splits snapshot and feed databases MUST supply a transactionally consistent watermark read — recorded as a mount obligation, not left implicit.

Ordering and bounds are deterministic: objects are sorted (domain, then entity id, then op class) at open, page boundaries are a pure function of the immutable object list and the byte cap, so repeated reads return identical pages (tested byte-for-byte across two full paginations). Pagination is byte-bounded (default 256 KiB, configurable) with the feed's no-starvation rule: a single oversized row is delivered alone on its own page (tested with a 1 KB payload under a 300 B cap).

## 3. One-transaction apply; interruption cannot advance the cursor

Client `applyPage` covers entity applies, the page-dedup row, the per-entity applied ledger, and the checkpoint advance inside ONE transaction. The SIGKILL pair brackets it exactly as T03/T04 did: a child killed mid-apply (blocked inside the transaction after its first row) leaves no entity row, no dedup row, and no checkpoint — the cursor provably never advances ahead of applied data; a child killed after the commit returned keeps everything, and re-delivery of the same page is a dedup no-op (lost-ack replay). Cursor advancement is monotonic (`MAX` guard): a replayed old page cannot move it backwards. An unregistered domain fails closed — the whole page rolls back, nothing partial persists. The completeness gate refuses `completeBootstrap` until applied rows equal the server manifest's object count, so a partially fetched bootstrap cannot mark itself done (tested).

## 4. Tombstones and manifest closure — stale rows cannot reappear

Deletes and scope changes are materialized as explicit `delete` rows: a scope-removed id arrives as a tombstone, and the client deletes its local row — replaying the full snapshot afterwards changes nothing (dedup skips; tested that the stale row never resurrects). For rebootstrap over existing data the completion step adds **manifest-closure reconcile**: rows present locally but absent from this snapshot's applied-entity ledger are dropped as stale, EXCEPT ids the pending-work probe reports as protected. Protection wins in both places a delete could touch: the closure reconcile preserves and *reports* them (`ReconcileResult.preserved`), and a tombstone targeting a protected id is **skipped and surfaced** (`ApplyPageResult.protectedDeletes`) — pending local work and its domain row stay intact for dispatch, and the conflict resolves through M03-T07 server outcomes. Nothing is discarded silently; that is the acceptance line "safe rebootstrap that preserves and reconciles pending local work instead of discarding it", proven end-to-end (protected row survives a server-side delete, is reported preserved, and the bootstrap still completes at the fresh watermark).

## 5. Expired and invalid cursors — typed rebootstrap, never a silent skip

Stale cursors surface as typed `resync_required` (the ADR-0011 "410 Gone" analogue carried over from the feed): an unknown snapshot id and a swept snapshot both produce it. Retention is explicit (`sweepSnapshots`): swept snapshots delete their objects but retain the manifest row with `state='swept'` so cursors into them get the typed signal rather than a confusing not-found. The recovery flow is tested mid-bootstrap (swept while applying → `resync_required` on the next page → abort → fresh snapshot → reapply → complete) and post-completion (cursor expired after server state moved on → abort → rebootstrap → reconcile with protection). `abortBootstrap` is the single typed reset: it forgets the scope's checkpoint (applying or complete), its page-dedup rows, and its applied-entity ledger — local domain rows and outbox pending work are untouched.

## 6. The feed handoff and what the consumer does next

A completed bootstrap ends at the snapshot's watermark; that value is the `afterSeq` the M03-T04 `FeedConsumer` resumes pulls with (pinned in the handoff test: checkpoint state complete, watermark = the feed cursor at open). The two checkpoint systems never mix: a completed bootstrap structurally refuses further snapshot pages (`misconfigured`), because post-bootstrap change delivery is the feed consumer's contract — incremental, deduplicated, and replay-safe per T04's evidence. The Flutter consumer of this bootstrap surface is the M04 first vertical workflow's local repository (daily log + photo), whose sync initialization will call exactly this open→apply→complete sequence; parity evidence flows through the M10 parity gate as recorded in the T03/T04 packets. No server-side domain feature is added here; the standing change-feed/Flutter-parity obligation for any future one is restated (v3 §10).

## 7. Test evidence and CI wiring

`packages/native_snapshot/test/snapshot.test.ts` runs **20 `node:test` cases against real on-disk SQLite** (Node built-in `node:sqlite`; the check tool refuses to run below Node 23), mapped to the acceptance matrix: S1 consistency/determinism/bounds (6 tests: materialization order, concurrent-write immunity, deterministic pagination, byte cap with no starvation, maxObjects rollback, source-failure rollback); S2 one-transaction apply (4: commit-together, SIGKILL mid-apply, SIGKILL post-ack with dedup replay, fail-closed domain); S3 tombstones (3: delete+no-resurrect, protected-delete skip surfaced, manifest closure); S4 expired cursors (4: typed `resync_required`, mid-bootstrap sweep recovery, rebootstrap preserving pending work, completeness gate); S5 pins and handoff (3: surface pins, migration contiguity/idempotency, watermark handoff). Two SIGKILL scenarios spawn real child processes (spawn-stable across 3 consecutive local runs). CI runs the suite as a new **"Run Native Snapshot Bootstrap Tests"** step in `lint_and_protocol` via `tool/check.mjs` (pinned `typescript@5.9.3`) inside the existing Node 24 block, after the sync feed step it hands off to.
