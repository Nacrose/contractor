## 1. Purpose and scope

This task is the automated fault matrix the register demands: one runner covering the failure space across local commit, server acceptance, feed delivery, checkpoint persistence, attachment transfer, and device recovery — with reproducible reports and BOTH durability engines real. Twelve SQLite legs run against real on-disk `node:sqlite` databases in this process and in SIGKILLed child processes; four PostgreSQL legs run against a disposable server (GitHub Actions `services: postgres:16` with the pinned MIT-licensed `pg@8.16.3` client via `NODE_PATH`). When the disposable PostgreSQL is unreachable on a host (as in this sandbox), the PG legs SKIP with an explicit marker and the CI run provides that engine's evidence — mocks may supplement but never substitute anywhere in this matrix. Every leg asserts the global invariants over the touched data: **I1** no lost accepted operation, **I2** no duplicate business effect, **I3** no cross-tenant disclosure, **I4** safe recovery at each covered boundary; each row of the emitted matrix carries the sanitized identifier discipline and the deterministic recovery action.

## 2. The twelve SQLite legs

Duplicate delivery (dedup ledger replay is a no-op; entity version advanced exactly once — I2); reordered delivery (the higher seq arrives first, the older seq late: applied once, the cursor MAX-guard never moves backwards); lost acknowledgement (server receipt exists, client replay records the ORIGINAL receipt exactly once, ledger never grows); late server commit (a seq commits BEHIND the cursor: the hole is visible, the next pull closes it, nothing is lost — the concurrent-writer variant is proven on PostgreSQL in P03, because SQLite serializes writers and an honest matrix does not pretend otherwise); expired/invalid cursor beyond retention (typed detection → reset → reapply under dedup); checkpoint loss and full replay (rebuild from the dedup ledger with ZERO duplicate business effect); concurrent devices (two real connections, busy_timeout, unique op identity collapses duplicate receipts while both devices' ops stay durable); permission revocation/cross-tenant read (scope-shaped queries return ZERO rows to another tenant — I3); attachment interruption (staging rows reconcile, partial objects never exposed as complete); process termination (SIGKILL child mid-transaction → WAL rollback on reopen, integrity_check ok, nothing partial); disk full (ROLLBACK-journal database with `max_page_count` → typed SQLITE_FULL code 13, automatic transaction abort, no partial rows, recovery after the bound is raised); interrupted migration (per-version transaction rollback → previous version, no partial DDL, re-migratable).

## 3. The four PostgreSQL legs (disposable engine)

The PG segment exercises what SQLite structurally cannot: true concurrent writers on the server's authoritative store. P01 transactional acceptance (domain version bump + op receipt in ONE transaction; a simulated crash ROLLBACK leaves nothing, the redo commits both); P02 exactly-once under same-op acceptance from a second device (unique op identity refuses the duplicate — the loser takes previously_accepted semantics); P03 cursor monotonicity under concurrent commits (`GREATEST`-guarded checkpoint updates out of order never regress); P04 terminated backend mid-transaction (`pg_terminate_backend` on an open transaction; a fresh connection finds the uncommitted work rolled back — server-side recovery). The legs are idempotent per run (tables cleaned at start) so the CI matrix reruns are reproducible.

## 4. What the matrix itself caught

Building the matrix surfaced (and fixed) two harness-level findings worth recording. First, the matrix's apply helper initially advanced the checkpoint only for NEW events — replaying after checkpoint loss wedged the cursor at 0; the REAL M03-T04 consumer already advances its checkpoint on every batch (dup or not, MAX-guarded), which the matrix now verifies as the required discipline rather than assuming it. Second, the disk-full leg demonstrated that SQLite auto-aborts the open transaction on SQLITE_FULL (the explicit ROLLBACK is a no-op afterwards) — the recovery contract is therefore "the failure IS the rollback", and the typed full error plus post-recovery re-apply is what the mount must guarantee. Both are exactly the kind of boundary knowledge M04 fault evidence will need to diagnose production behavior.

## 5. Test evidence and CI wiring

`packages/native_faultmatrix/test/matrix.test.ts` runs **14 `node:test` cases** (12 SQLite legs + the PG leg group + the report-completeness pin), stable across 3 consecutive local runs; the emitted markdown matrix lists every row with boundary, engine, invariant, deterministic recovery, and result (PASS/SKIP-with-reason/FAIL — a FAIL anywhere fails the check). CI runs it as a new **"Run Native Fault Matrix (real SQLite + disposable PostgreSQL)"** step in `lint_and_protocol` with a job-level `services: postgres:16` container and the pinned `pg@8.16.3` client installed to `$RUNNER_TEMP` (ADR-0014: MIT license, no repo dependency added); `MATRIX_REPORT_PATH` writes `docs/reports/M03/fault-matrix-results.md` on every CI run. The Flutter parity tests linked here are the per-package suites already recorded in the M03 packets (the matrix composes their disciplines); the server-side domain writers covered by the feed remain exactly the M03-T04 pilot (daily-report/field-submission) — the matrix adds no domain feature and no feed semantics change.
