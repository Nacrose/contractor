## 1. Purpose and scope

This task makes sync health observable NOW so M04 fault evidence can be diagnosed. The package (`@contractor/native-observability`, zero runtime dependencies) provides the three surfaces the register names: a fail-safe crash-report sanitizer that every Dart, native, and Rust panic path reports through; a server sync-metrics registry with tenant-safe aggregation; and the device sync-health read model derived from durable state. There is deliberately NO telemetry transport here — the surfaces define WHAT may be observed and HOW it must be reduced; the mount binds transports (and the server binds its own metrics endpoint) outside this contract. The device read model runs against REAL SQLite mirrors of the outbox and checkpoint shapes (WAL + synchronous=FULL), and the staged transition evidence drives REAL state updates and REAL metric observations through the mount's boundary composition point.

## 2. Crash redaction — drop-first, fail-safe, per component

`scrubCrashReport` reduces ANY captured panic context to the safe shape: only allow-listed attribute keys survive (`CRASH_SAFE_ATTRIBUTE_KEYS`: ids, states, counters, device metadata — never session cookies, draft bodies, or authorization headers), every surviving value is scrubbed of secret-like substrings (GitHub tokens, JWT segments, Bearer headers, long hex runs, password/token assignments) and payload-like content (JSON bodies become `[PAYLOAD]`), length-capped, and stack FRAMES never export at all — only the frame count. The redact-then-cap ORDER is itself tested (a test caught the first implementation capping before redacting, which let a JSON body survive truncated). Tested per component — dart (private draft body + session cookie + token inside a frame string), native (access token in the panic message), rust (long hex digest inside a JSON body) — with the sentinel asserting NOTHING payload-like appears in the serialized report. Malformed contexts fail safe: non-object attributes, non-array frames, and NaN timestamps still reduce to the safe shape, and an unscrubbable context has a typed minimal fallback (`unreportable`). The M03-T02 redaction vocabulary is re-declared for zero-dep isolation; the mount binds the identity implementation where both exist.

## 3. Server metrics — tenant-safe aggregation by construction

The `SyncMetrics` registry records one observation per sync request at the service boundary, labeled with the M03-T07 outcome table (`requests`, `accepted`, `replayed`, `rejected`, `conflicted`, `revoked`, `auth_required`, `dependency_blocked`, `retryable`) plus feed lag and checkpoint age samples and the M03-T06 attachment retry/error counters. The tenant-safety rule is structural: the GLOBAL snapshot contains outcome counts and tenant-safe aggregates ONLY — a test records observations under two deliberately secret tenant ids and asserts the serialized global snapshot carries neither identifier nor any per-tenant breakdown (the shape has no `tenantId` and no `byKind` field at all). Per-tenant numbers require the explicit authorized `snapshotTenant(tenantId)` surface (per-kind breakdown included; an unknown tenant is a typed `not_found`), and an observation without a tenant scope is `misconfigured` — the aggregation gate itself is tested. Feed lag and checkpoint age aggregate as tenant-safe min/max/avg.

## 4. Device surface — honest by construction, no false success

`buildDeviceSyncHealth` derives its read model ENTIRELY from durable state through the `SyncHealthSource` port (REAL SQLite in evidence): pending-operation count and oldest pending age (in-flight included), per-scope last accepted cursors, conflict and dependency-blocked counts, and surfaced rejection reasons in sanitized shape. The honesty rule is the acceptance line verbatim and is pinned by test: `synced: true` ONLY when no pending work exists, no fresh rejection is unsurfaced, and nothing is conflicted or blocked — pending/in-flight work, conflicts, blocked ops, or a fresh rejection each yield `synced: false` with explicit reasons. Rejections remain visible in history after the freshness window passes (the surface stops counting them as blocking, never hides them). This is the anti-false-success guarantee the register demands: a UI binding this surface cannot show a green "synced" badge while work is pending or a rejection is fresh.

## 5. The staged rejection/retry scenario — device and server agree at every transition

The register's staged scenario is proven as transition evidence where device state and server telemetry move TOGETHER: a REAL-SQLite pending-op row walks retryable → retryable → accepted through the scripted sync boundary (the mount's composition point — each step applies the outcome to the REAL rows AND records the REAL observation), and at every stage the device health surface and the metrics snapshot agree (stage 1: `synced:false`, 1 pending, 1 retryable; stage 2: still 1 pending, 2 retryable; stage 3: `synced:true`, 0 pending, cursor at the commit-order seq, 1 accepted). The rejection scenario mirrors it: a conflict is visible on BOTH surfaces (`conflicts: 1` + `conflicted: 1`), and the recovery re-acceptance returns both to green together. Redaction holds at every stage: payload sentinels never appear in the serialized health or metrics output even when failure details are flowing.

## 6. Test evidence and CI wiring

`packages/native_observability/test/observability.test.ts` runs **18 `node:test` cases** (stable across 3 consecutive runs) against REAL SQLite for the read model: S1 crash redaction (4, per component + fail-safe); S2 server metrics incl. tenant-safety (5); S3 device surface incl. the no-false-success pin (4); S4 staged scenarios with redaction (3); S5 surface pins (2 — the full `SyncMetrics` prototype is pinned). CI runs the suite as a new **"Run Native Observability Tests"** step in `lint_and_protocol` via `tool/check.mjs` (pinned `typescript@5.9.3`) inside the Node 24 block, after the orchestrator step. The Flutter parity surface is the device sync-health read model: the M04 first vertical workflow's sync UI binds this exact shape (pending count, oldest age, per-scope cursors, rejection reasons, honest `synced` flag) through the mount; the server-side event/change-feed mapping for metrics is the service-boundary observation call recorded in §3 — no feed semantics are changed here, and no server-side domain feature is added.
