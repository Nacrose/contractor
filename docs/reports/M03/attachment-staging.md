## 1. Purpose and scope

This task builds the attachment half of the M03 sync engine: transfer attachment bytes independently from domain acceptance while keeping registration and file durability consistent. The package (`@contractor/native-attachment`, zero runtime dependencies) implements the full staging protocol above the durable state the M03-T03 outbox already records (the outbox `attachment_stage` row is the pending-work summary input; this package owns the transfer protocol — the mount composes them, no cross-package import): stage bytes to a durable object store, compute AND verify a digest at both integrity boundaries, durably finalize storage with an atomic rename, and only then register the attachment with the server via a chunked, resumable upload. An append-only sanitized reconciliation journal plus deterministic resume/retry drives every interruption point to recovery; a global orphan sweep reclaims bytes that no journal row references. Like T03/T04/T05 it defines a structural `SqlDriver` port matching `node:sqlite`'s `DatabaseSync`, and the evidence below runs against **real SQLite, a real on-disk object store, real SHA-256, and a disposable server/object fixture backed by its own real SQLite + directory** — no mocks as durability proof.

The package ships **no domain schema and no file-IO of its own**: byte storage goes through the injected `ObjectStore` port (durable write = temp + fsync + atomic rename is the implementation contract), source re-reads through `SourceReaderPort`, digest through a fail-closed `DigestPort` (the manager refuses to open without a real SHA-256 implementation — no fallback digest exists), and server registration through `AttachmentRegistrarPort`. The manager class surface is pinned by test to its exact prototype method set (10 public protocol methods plus the private helpers, full prototype pinned) — no domain writers on any port.

## 2. Ordering and digest verification — structural, not conventional

The protocol order is enforced by the state machine, not by convention: `register` refuses anything not `finalized` (typed `illegal_transition`, tested), `finalize` re-verifies the digest against the FINAL object bytes, and the digest is computed at stage time and then VERIFIED by re-reading what actually landed in the store — write-integrity proof at both boundaries (tested: tampering with the staged object after staging turns `finalize` into a typed `digest_mismatch` recoverable failure whose deterministic recovery is a full re-stage from source). Bytes reach the server only after durable local finalization, and the registration receipt is recorded in the SAME transaction as the `registered` row — the receipt is the only proof a server registration happened, and nothing is ever auto-registered locally. Re-staging an existing id restarts the transfer cleanly without duplicating rows (tested).

## 3. Interruption and the reconciliation journal

Every state change writes an append-only journal event (`stage_started`, `staged_verified`, `finalized`, `upload_opened`, `chunk_ack`, `registered`, `failed`, `recovered`) in the same transaction as the row update. Event details are SANITIZED and pinned by test: ids, digests, offsets, byte counts and receipt ids only — a sentinel embedded in the payload never appears in any journal row (journal details are strict JSON). Four SIGKILL scenarios with real child processes cover the interruption space (spawn-stable across 3 consecutive local runs): killed mid-stage (partial temp file on disk, row `staging`), killed mid-finalize (file already renamed, database row still `staged` — the file/database gap), killed mid-upload (server holds the first chunk in its durable fixture state), and killed AFTER server completion but before the local receipt is recorded (the lost-ack scenario). Recovery is by reconcile, not by hope: `resume` re-reads reality (object store + server) and drives the protocol stage→finalize→register in one pass to its next deterministic stop. Partial and orphaned objects are never exposed as complete attachments — `list(completeOnly)` is EXACTLY the registered rows (tested at every interruption point), and `sweepOrphans` (global — the store has no account dimension, so a per-account sweep would wrongly collect other accounts' objects) removes only keys no journal row references.

## 4. Resume from the server's authoritative offset

The upload loop treats the SERVER's `receivedBytes` as the sole authority; client `chunk_ack` events are hints. The mid-register SIGKILL test proves no-byte-resend numerically: after the kill, the fresh process sends exactly `total − serverOffset` bytes (the fixture also structurally rejects any chunk whose offset is not the server's current received count, so a stale-offset resend cannot silently succeed). The lost-ack test proves registration idempotency end-to-end: re-completing an already-completed upload returns the SAME receipt, zero bytes are re-sent, and the local row records the identical receipt the fixture holds. Pre-existing server progress is honored the same way (tested: seed half the upload, the register sends exactly the remainder). Resume triggers are one mechanism, not three: app launch, foregrounding, and manual sync all land on `resumeAll`/`resume(id)` over the same journal — OS background transfer remains an opportunity that can only ADD a trigger, never the only recovery path.

## 5. Typed recoverable failures — pending data is never silently dropped

Every failure maps to a typed recoverable state that preserves all pending data (bytes, journal row, events, source identity): `retryable` (transient server error → bounded backoff, `attempts` incremented, `resumeAll` skips until due — surfaced as still-pending, not dropped; manual `retry` forces), `rejection` (policy — manual retry after fix), `revoked` (retry after re-auth), `storage` (server quota or local store exhaustion via the documented `TransferError('full')` contract), `digest_mismatch` (local or server integrity — recovery ALWAYS re-stages from source, the full clean re-transfer), and `source_missing` (the source vanished before a staging-row resume — recoverable when the user re-provides the file). Each is tested with the failure injected at the fixture boundary (never by touching package code), asserting: typed kind + resume step recorded, bytes/source/journal intact, the attachment is not exposed as complete, and the recovery action completes the transfer. The verification-failure path is honest about limits: a `digest_mismatch` that repeats keeps surfacing as recoverable-with-preserved-data rather than being auto-discarded.

## 6. Test evidence and CI wiring

`packages/native_attachment/test/attachment.test.ts` runs **22 `node:test` cases against real on-disk storage** (real SQLite journal via `node:sqlite`, real directory object store with fsync+rename durability, real SHA-256, and a disposable server/object fixture with its own real SQLite + segment directory — state that deliberately survives the crash-child process boundary, which an in-memory mock could not prove), mapped to the acceptance matrix: S1 ordering + digest boundaries (4 tests); S2 interruption/reconciliation (5, four with real SIGKILL children); S3 resume triggers incl. server-offset honor (4); S4 typed recoverable failures (7); S5 pins, migrations, redaction, account isolation (3). Account isolation is enforced by the query shape (every row keyed `(id, account_id)`; cross-account get/list/sweep/stage tested). CI runs the suite as a new **"Run Native Attachment Transfer Tests"** step in `lint_and_protocol` via `tool/check.mjs` (pinned `typescript@5.9.3`) inside the existing Node 24 block, after the snapshot step. The Flutter consumer of this surface is the M04 first vertical workflow's attachment path (daily-log photo): it will call exactly stage→finalize→register and consume the typed failure states for its sync UI; parity evidence flows through the M10 parity gate as recorded in the T03/T04 packets. No server-side domain feature is added here; the standing change-feed/Flutter-parity obligation for any future one is restated (v3 §10).
