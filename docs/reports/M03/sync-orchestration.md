## 1. Purpose and scope

This task is the POLICY layer of the M03 sync engine: coordinate ordered pending operations, retries, dependencies, network/power conditions, and response handling across native and browser clients. The package (`@contractor/native-orchestrator`, zero runtime dependencies) carries BOTH sides — a client `Orchestrator` drain policy over the M03-T03 outbox's durable pending operations (the `PendingOperationSource` port mirrors the outbox's real method shape 1:1, so the mount adapts it without translation), and a server `ServerSyncService` that validates the versioned envelope, REVALIDATES claims authoritatively, answers duplicates from an op-id ledger, applies through a domain port, and emits exactly the eight typed outcomes. The orchestrator owns NO storage of its own (no migrations — persistence stays in the outbox, extended at the mount via its documented `extraMigrations` mechanism for the blocked/conflict surfaces); the evidence fixtures back both sides with REAL SQLite (node:sqlite).

There is deliberately ONE suite for BOTH mounts: native and browser clients bind different ports (transport, environment, identity) but the envelope construction, outcome classification, retry policy, and dependency gating are this shared, test-pinned code — "matching response semantics" is structural, not aspirational. The pilot domain apply is the daily-report submit with base-version conflict detection (M03-T04's change-feed domain); its acceptance outcome carries the commit-order `serverSeq` the feed consumer continues from.

## 2. The versioned envelope and authoritative revalidation

Every envelope carries ALL the v3 §5.3 fields, pinned structurally by test: sync protocol version (1; bumping requires a [PLAN-AMEND] decision), operation identity (the outbox opId — the idempotency key), device identity (M03-T02 registration), account, namespaced operation kind (T01 discipline), scope claims, sha-256 payload digest, dependency identity, attempt counter, and send time. The server gate RECOMPUTES the digest over the received payload before anything else can happen — a tampered payload is a typed `rejected` and the domain is provably untouched (tested). Scope claims are validated for SHAPE at the gate but their TRUTH is revalidated by the injected `ServerAuthorityPort`: a stale or stolen tenant claim in a well-formed envelope still yields `revoked` (tested) — client claims are never trusted, which is the acceptance line verbatim.

## 3. The eight outcomes, each with a tested destination

The outcome table maps exactly to v3 §5.3: `accepted` records the receipt AND commit-order serverSeq on the pending record (feed continuation intact, tested); `previously_accepted` records the ORIGINAL receipt exactly once on lost-ack replay (tested end-to-end: the transport simulates connection death AFTER the server accepted — the real lost-ack, not a mocked outcome — and the replay returns the identical receipt with the domain applied exactly once); `conflict` surfaces typed on the pending record with the payload PRESERVED and no re-dispatch while conflicted (app resolution is a separate, explicit step); `rejected` is terminal with a sanitized reason (asserted free of payload content); `revoked` and `authentication_required` STOP the drain mid-batch, surface the auth event (the M03-T02 credential-wipe input, composed via `AuthEventSink`), requeue the interrupted op, and preserve every pending record (tested: the subsequent op is never dispatched); `dependency_blocked` fires when the SERVER disagrees with the local dependency view — the server's word wins and the dependent is marked; `retryable` honors a server-suggested delay when present, else the local jitter schedule. An op the server finds to have an unmet prerequisite is refused server-side too (defense in depth; tested).

## 4. Ordering, bounded jitter retries, and the one real policy bug found

Dependency ordering is enforced twice: locally, a dependent dispatches only when every `dependsOnOpIds` entry is accepted — a pending prerequisite is NEVER overtaken (skipped dependents stay pending; a rejected/blocked/conflicted prerequisite fails the chain terminally as `dependency_blocked`), and the same-pass case is tested (parent accepted first, child dispatches in the SAME drain after the acceptance lands). Retries are BOUNDED with FULL jitter (`random() × min(cap, base·2^attempt)` from a deterministic injected `RandomPort`, so every delay is assertable in `[0, ceiling)`): the test drives a dead network through the full budget and proves the op is SUSPENDED at the cap — pending, never dropped, payload intact for manual retry, no further auto-dispatches. The cap surfaced a real policy bug during development (requeue-with-null made a cap-exhausted op immediately due again — unbounded in disguise); the fix (suspend-at-cap in the drain walk) is itself covered by the test that caught it. Single-flight per instance prevents concurrent double-dispatch; a crash between dispatch and response recovers through the in-flight recovery walk (`recoverInFlight` requeues before the batch is read — the ledger makes the replay idempotent).

## 5. Foreground without a scheduler; background gated; hints are hints

Foreground `drain()` requires nothing but the ports: no OS background scheduler, no execution-environment gate (tested with NO environment port bound at all). Background attempts (`drainInBackground`) consult the `ExecutionEnvironmentPort` first and return an empty result when constraints are unmet — pending work byte-identically untouched (tested), and proceed through the identical policy when suitable. Push notifications are HINTS with exactly two powers: start a drain when one is not running, and do nothing otherwise — re-entrant hints during a running drain coalesce to `null` (tested by calling `hintAvailable` from INSIDE the transport), and a hint cannot bypass backoff accounting (an not-yet-due op dispatches nothing). No hint path fabricates or records outcomes; acceptance receipts come only from the server.
