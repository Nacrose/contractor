## 1. Purpose and scope

This task turns the M01 engine-level durability proof into the **repository contract** the sync engine actually uses: a versioned SQLite schema with migrations, the one-transaction save boundary that makes a local mutation and its pending sync operation durable *together*, account isolation, private-draft and attachment-staging state, and an explicit-only retention policy. The package (`@contractor/native-outbox`, zero runtime dependencies) defines a structural `SqlDriver` port that matches Node's built-in `node:sqlite` `DatabaseSync` surface, so the durability evidence in this repo runs against **a real SQLite database** — the acceptance line "mocks alone do not count" is satisfied in CI itself, not deferred to the app repo. The app mount later binds the same port to its native driver (sqflite_common_ffi/Drift underneath) without changing this code.

The repository is a **durability boundary, not an authority**: acceptance receipts are recorded only from server outcomes, and there is no code path that accepts, uploads, or deletes pending work on its own. This is the local half that M03-T02's pending-work gate reads (`pendingWorkSummary` returns exactly the `PendingWorkSummary` shape the identity contract's gate consumes — shape-compat pinned by test) and that the M03-T07 orchestrator will drive (dispatch batches, backoff, dependency ordering). No server-side domain feature is introduced; the standing change-feed/Flutter-parity obligation for any future one is restated in §7.

## 2. The save boundary: one transaction, or nothing

`saveMutation` opens a `BEGIN IMMEDIATE` transaction, runs the caller's domain-table writes (pure SQL against app-owned tables — business rules stay in the domain service), inserts the `pending_op` row and its dependency rows, and commits — all in ONE transaction. Any failure rolls back **both** sides: a domain callback that throws after its own insert leaves neither the domain row nor the pending op (tested), and a dangling dependency reference fails the whole save with a typed `constraint` error before anything persists (foreign keys are enforced by `openOutbox`). The same boundary holds for engine-level failures — disk-full and busy are typed and rolled back in §4 — and for process death in §5: an unacknowledged save leaves *nothing*, and an acknowledged save (the commit returned) leaves *everything*. This is the exact "no lost accepted operation / no partial visibility" pair the M03 exit demands, now proven at the repository level rather than only at the engine level.

## 3. Versioned schema and interrupted-migration recovery

The shipped schema is versioned (`OUTBOX_MIGRATIONS` v1 baseline + v2 dependency table, contiguity validated up front): `pending_op` (state machine CHECK-constrained to pending/in_flight/accepted/rejected, attempts, backoff gate, digest, durable `accepted_receipt`), `op_dependency` (FK-cascaded ordering edges for the v3 §5.3 envelope), `private_draft`, `attachment_stage`, and `meta` (schema_version). Each migration runs in its own transaction *including* the version bump, so an interrupted migration rolls back to the previous version and the database stays re-migratable: the recovery test injects a failing v4 after a good v3, asserts the version lands at 3, prior data survives, and a clean reopen heals forward. App-owned domain tables extend the schema through the same mechanism (`extraMigrations` with higher versions — the tests register a sample `daily_log`), and a database ahead of the provided set is left untouched (forward-compatible open).

## 4. Busy, disk-full, corruption — typed at the boundary

Every engine error surfaces as a typed `RepositoryError` (`mapSqliteError` masks SQLite's extended result codes to primary codes first): `busy`/`locked` (5/6), `full` (13), `corrupt` (11), `notadb` (26), `constraint` (19). The tests reproduce each against the real database:

- **Busy/locked:** a second connection holding `BEGIN IMMEDIATE` makes the repository's save fail typed `busy` after `busy_timeout`; after the holder commits, the retry succeeds. Retry orchestration (jitter, backoff) is M03-T07's job — the repository's obligation is to surface the engine truth instead of swallowing it.
- **Disk-full:** `PRAGMA max_page_count` squeezes the database to zero headroom; a 512 KB payload fails typed `full`, rolls back, and leaves the previously committed op intact with `integrity_check` ok. (Engine quirk recorded in the test: `max_page_count=0` is a same-connection no-op on this build after a FULL error — the limit is released explicitly instead.)
- **Corruption:** after a clean close, clobbering the 16-byte header magic makes the next open fail typed `notadb` — detection, not repair. Repair policy is deliberately out of scope here: the explicit `purgeAccount`/rebootstrap paths (M03-T05) own recovery, because silently rebuilding a corrupted local store is exactly the kind of unrequested deletion the offline discipline forbids.

## 5. Process termination: kill-before-commit vs kill-after-ack

Two SIGKILL tests spawn a real child process against the same database and mirror the M01 rig's methodology at the repository level. *Kill with the transaction open:* the child starts a save whose domain callback signals READY and blocks; the parent SIGKILLs it; on reopen, neither the domain row nor the pending op exists and integrity holds — uncommitted work never half-survives. *Kill after acknowledgement:* the child completes the save and prints ACKED **only after `COMMIT` returns**; the SIGKILL afterwards leaves both rows intact — no lost accepted operation. Together with §2 this brackets the durability claim exactly: the acknowledgment is the durability boundary.

## 6. Account isolation, private drafts, and explicit-only retention

Every row is account-scoped and every read takes an account scope — the API shape makes cross-account reads impossible without bypassing the repository: B's batch never returns A's ops, `getOp`/`getDraft` with the wrong account return null, and the pending-work summary counts only the asked-for account (tested). `pendingWorkSummary` feeds M03-T02's gate, so logout/account switch surfaces pending shared work, private drafts, and staged attachments — surfacing, not deciding. Private drafts are local-only rows the user explicitly deletes by id; attachment staging is a CHECK-constrained state machine (staging→staged→finalized→registered, failed from any pre-registered state) that M03-T06's transfer protocol will drive. Retention is explicit-only, pinned structurally: the class surface contains no evict/trim/LRU/prune primitive (test on the prototype), and the two deletion paths are tested for exactly-what-they-say — `deleteAcceptedBefore` removes only accepted-with-receipt history (cutoff semantics included), leaving pending, rejected, drafts, and attachments untouched; `purgeAccount` wipes strictly one account inside one transaction. Pending operations, attachments, and private drafts are durable data, never cache.

## 7. Authority, parity, and non-goals

The domain service stays the authority: `recordAccepted` *requires* the server receipt, `recordRejected` requires the server reason, and nothing on the client auto-accepts — the repository records outcomes, it never renders verdicts. Dependency ordering is enforced for dispatch eligibility (a dependent op is not surfaced while any prerequisite is pending/in-flight; acceptance unblocks it), which the M03-T07 orchestrator and the v3 §5.3 envelope's dependency identity build on. The Flutter consumer of this contract is the M03-T07 orchestration surface with parity evidence flowing through M10; any future server-side domain feature must still name its change-feed integration and Flutter-parity path in its own packet (standing constraint 3 — none is added here).

**Non-goals:** no transport/sync orchestration (T07), no attachment byte transfer protocol (T06 — this package owns the durable state rows only), no snapshot/bootstrap (T05), no server-side changes. Follow-ups: the app mount binds `SqlDriver` to the shipping native driver and records its own journal/sync pragmas per the M01 rig's follow-up note; the exact receipt format is the server session/sync service's to define (T04 feed work).

## 8. Test evidence and CI wiring

`packages/native_outbox/test/outbox.test.ts` runs **19 `node:test` cases against real on-disk SQLite** (Node built-in `node:sqlite`; the check tool refuses to run below Node 23): migration contiguity/idempotency, domain-migration extension, misconfiguration rejection, interrupted-migration rollback+heal; one-transaction save with both-sides-visible and both-sides-rolled-back; FK-typed save failure; busy typed+retry; disk-full typed+rollback+integrity; corruption typed at open; two SIGKILL scenarios (mid-transaction rollback, post-ack survival); lifecycle transitions with illegal-transition typing and receipt requirements; dependency-ordering gate; cross-account invisibility + summary shape; retention exactly-once semantics; purge isolation; attachment machine edges; and the no-eviction structural pin. Suite green 3/3 consecutive local runs (spawn-timing stable). CI runs it as a new **"Run Native Outbox Repository Tests"** step in `lint_and_protocol` via `tool/check.mjs` (pinned `typescript@5.9.3`), with a dedicated `setup-node@v4` Node 24 step immediately before it (`node:sqlite` is unflagged there; all earlier steps keep Node 20) — placed so no subsequent step in the job depends on the Node version.
