# M01-T12 — PDF, DWG, and XLSX dependency matrix

**Status:** comparative evidence; no production dependency selected.  
**Inspected:** M00/M01 reports, source and lockfiles in the separate product checkout `Construction-manager-0.2` (read-only), and current upstream package/vendor documentation on 2026-10-09.  
**Purpose:** compare actual and candidate support by platform, license, fidelity, offline behavior, and cost/deployment constraints. Package claims are identified separately from results reproduced in this repository.

## Executive summary

The existing product paths are JavaScript/TypeScript in the browser, with a conditional server-side DWG converter; the Flutter prototype does not yet integrate PDF, DWG, or XLSX packages as production dependencies. T10's `pdfrx`/PDFium evidence establishes a useful lead for a real-PDF prototype, but only on a generated one-page web fixture. The product's current PDF.js implementation remains the web reference. The current DWG reader provides explicitly limited legacy support, with newer files requiring a converter. The XLSX adapter is local JavaScript and already round-trips a useful tested subset, but it is not a promise of complete Excel feature fidelity.

No cloud-only converter meets the offline editing requirement for a native client. A remote conversion service may be an optional online convenience, but cannot be the only path for editing a locally available PDF, DWG, or XLSX while disconnected.

## Decision inputs and follow-up

1. Keep the current PDF.js route as web reference behavior. Advance `pdfrx`/PDFium only as the lead for T10's real binary-PDF prototype. Create or source sanitized binary fixtures for a 100+ page / approximately 200 MB package, dense vector page, scanned page, rotated/mixed-size pages, and malformed or encrypted files; M00's 120-page CanvasDoc fixture is not a binary PDF. Require network-disabled web and native builds, bounded memory/cache, cancellation/disposal results, and output comparison before selecting a package. A CDN-dependent web path cannot be the only offline path.
2. Keep the DWG TypeScript reader's support label explicit: AC1012, AC1014, and AC1015 legacy read. Treat modern DWG as conditional server conversion with DXF output and version/entity caveats. Do not bundle or host LibreDWG or ODA based on process separation or “free download” language alone; verify exact legal terms, supported builds, fidelity, and cost before an adoption decision. RealDWG remains a commercial alternative requiring a quote and target-platform confirmation.
3. Keep the existing XLSX adapter and engine for the tested application subset while maintaining a clear compatibility envelope. Do not claim full Excel fidelity or add cloud conversion as a substitute for local file handling. Review the old `@e965/xlsx` fork's maintenance/provenance and test additional sanitized real-world workbooks before changing package selection.
4. Record PDF, DWG, and XLSX separately in any product capability matrix. Mark unsupported native integrations and conditional network/deployment requirements explicitly. A cloud-only candidate is unacceptable as the sole route for native offline editing; remote conversion may only supplement a local-capable workflow.

## Limitations

This is a source/package/vendor review, not a new interoperability benchmark or legal opinion. Platform support and licenses can change. The separate product checkout was not modified. No converters or packages were installed or selected. The documented platform tiers in M00 remain proposals until the M01 gate; this report distinguishes current product implementation, prototype evidence, and vendor claims rather than silently upgrading a support promise.
