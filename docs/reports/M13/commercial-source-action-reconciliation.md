## Reviewed service behavior

- BOQ reads and comparisons require `project.boq.view`. Create and inline update require `project.boq.edit`; delete uses `project.boq.delete`; locking uses `project.boq.lock`. Create/update/delete/duplicate honor the project BOQ lock and individual item lock where applicable. Codes are project-unique; edits recheck the row inside a transaction, and amounts are recalculated as quantity × contractual rate.
- Duplicating a BOQ item assigns a non-colliding code and copies its direct ingredients, rate analyses, ingredients, and provenance into the same project. Listing includes execution totals derived from daily-program actual quantities; comparison calculates a selected rate analysis and reports missing/incomplete/complete status and contract margin.
- Contractual BOQ rates remain explicit values. Engineering rate analysis is separate: fixed ingredient costs are grouped by material/labor/equipment/overhead; percentage provisions are calculated in saved order against their selected base; batch size determines the unit rate. Resource-demand calculation excludes percentage provisions and overhead and scales batch ingredients to BOQ quantity.
- Project rate profiles require BOQ view/edit permission. Applying a profile is edit-only, requires a preview fingerprint, verifies the profile and analysis belong to the same project, rejects a locked BOQ/item, and commits serializably. This prevents applying rates from a stale preview or a guessed cross-project analysis ID.
- Rate catalogs have three distinct scopes. Global create/edit is superadmin-only; organization scope requires `org.inventory.edit` (or org admin); project scope requires `project.materials.edit`. Reads use the matching view grants. Catalog materials and rates must share scope, and a new org/project catalog can only inherit from its permitted parent scope. This is separate from project rate-analysis editing, which uses the BOQ grant.
- BOQ version creation snapshots a non-empty current BOQ with its rate-analysis ingredients/calculation version and retries numbering conflicts. Approval is a compare-and-swap from draft, requires `project.boq.lock`, and locks the project BOQ in the same transaction. Version diffs compare a snapshot with live BOQ or another version and verify both versions belong to the project. A separate project lock action can lock or unlock under the same permission; the Contractor workflow must evidence the intended approved-baseline policy explicitly.

No BOQ, rate-analysis, profile or catalog operation appears in the field outbox whitelist. These are online server actions; none is durably cached as an offline read by the exact query whitelist. Tests named by M00 are present in the pinned source tree, but this inventory does not claim they ran or passed.

## Rate-library route and catalog controller review

On `ROUTE-111`, the page gates the Materials Catalog tab with `project.materials.view`, the Rate Catalogs tab with BOQ view, and passes BOQ edit as `CatalogRatesLibrary.canWrite`. The catalog router uses `project.materials.view/edit` for project-scope reads and writes. This leaves a grant mismatch: a user with BOQ access but no materials grant can see the rate-catalog tab and write controls, while the queries or mutations are denied; a materials editor without BOQ edit may be unable to use project-catalog actions that their server grant permits. Align the page gate with catalog-scope authorization and keep rate-analysis permissions separate.

The controller lists catalogs, loads the selected catalog, and automatically synchronizes an empty catalog when the caller-facing `canWrite` flag is true. That effect is an implicit mutation on viewing the tab: it idempotently creates missing rate entries using each material's default rate (often zero) for every catalog district. The server rechecks project materials edit permission and performs upserts transactionally, so the UI can show a permission error after attempting this background write. Make this a deliberate user action or provide an explicit state explaining why entries are being created.

Rate edits are locally buffered and saved on blur or Enter through `setRate`; server validation rejects negative values and enforces same-scope material/catalog ownership, then upserts the entry and appends a newly used district to the catalog. CSV import matches rows by exact material name and optional specification, then sends one `bulkSetRates` call (maximum 500 entries) whose rows are validated and written in one transaction. The client parser uses simple comma splitting for headers and a regex for row values, silently ignores unknown or unmatched materials, has no file/row limit, and does not reconcile district columns against the selected catalog before mutation; an oversized import is rejected as a whole by the server. CSV export uses raw catalog items rather than current search/category filters and writes zero for missing district rates. Catalog copying, district editing, fiscal-year switching and multiplier flows are delegated to separate dialogs and are not included in this controller subset.

On this project route, the callback passes the source-scope material ID directly into `bulkSetRates` for the project catalog; the server requires the material to belong to the target project scope, so copying parent-catalog rates fails unless the source material ID is coincidentally a project material ID. The supported `importFromParent` server path has the required source-to-target material mapping, but this dialog does not use it. Contractor should show one row per material, offer an explicit source-to-destination district map, and copy through the scope-aware import path.

The material sync dialog previews global-to-organization or organization-to-project catalog additions and lets users select new entries by item, group, category or all. Already imported entries are shown disabled. The server checks the target scope's edit grant, enforces the parent hierarchy, validates selected source IDs and caps a request at 1,000 materials. It creates or links target catalog materials and project resource rows, then imports matching rate entries with provenance. Each material and its rate import is committed in separate tenant transactions, so an error partway through can leave a partial but idempotent import; retry can finish the remainder. The dialog displays the server error and preserves selection on failure, but does not cap selected rows at 1,000 and remains dismissible during import. Its displayed checkbox has an empty `onChange`; selection is handled by the parent row click, so the checkbox itself is not keyboard-operable. These are partial-progress and accessibility behaviors to preserve or improve deliberately.

## Project material-catalog register review

The project rate-library page renders its Material Catalog tab through `AdminMaterialCatalogPage` with project scope and a `canEditProjectMaterial` flag. The page reads at most 500 catalog materials and does not request another page, so larger catalogs are silently incomplete in the tree, category list and bulk-selection view. Search is sent to the same bounded query. The server verifies project membership for reads and project-writer access for create, update and delete; the page permission flag controls visibility only and the server remains the write boundary.

The register's “Undo delete” control cannot currently work: `deletedHistoryStack` is initialized empty and never populated. Its handler calls `createMaterial`, which would create a new catalog identity rather than restore the old one; for archived rows, the server's duplicate lookup includes inactive rows and can reject that recreation. The project page also permits archiving selected rows but hides the Archived toolbar and archived table for project scope. When `showArchived` is set from another state, the project query can return inactive rows, but the rendered tree has no restore control; the restore mutation is only wired to the non-project `ArchivedCatalogTable`. Thus a project archive has no recovery path in this UI even though the backend supports `updateMaterial({isActive: true})`.

Single-item and category delete dialogs show reference impact before acting. The server rechecks references under a material-scope transaction and hard-deletes only unreferenced rows; referenced rows are archived. Bulk deletion processes IDs in separate transactions and writes one audit record after the loop. A failure partway through can therefore leave a partial result without the final audit record. Both delete dialogs close immediately after dispatching the mutation, so the user can lose the result/error context while it is still running and can repeat the action. The category dialog's “Delete Unused + Archive Referenced” operation is only offered to global admins, while the project tree omits category-level archive actions entirely.

The Archived view query uses `activeOnly: false` and the table does not filter inactive rows, so it presents active and archived materials together while labeling the full result as archived. Its Restore action calls `updateMaterial({id})` without `isActive: true`; the server leaves the active flag unchanged, but the UI reports “Restored item.” The purge button likewise calls `purgeArchived({})`: the server interprets omitted scope as global and requires global-admin permission, so an organization catalog cannot purge its own archive and a global admin using that view purges the global archive instead. The purge server also processes at most 1,000 archived records per call.

The importer defaults to organization scope and its parent does not pass the page scope, so “Import & Deduplicate” from the global catalog imports into the caller's organization instead of the global catalog. It splits every line on commas, tabs or pipes, so those characters in a material name or quoted CSV field are not preserved. The server caps tally and commit at 500 rows, but the UI has no row/size validation before calling it. “Link Existing” only increments a response counter in `commitImport`; it stores no mapping, alias or link, despite the success toast claiming rows were linked. Import commit is transactionally all-or-nothing, and the server rechecks target IDs in the destination scope.

The merge preview and execution enforce matching material scope and tenant/project membership; execution remaps references, merges aliases, records `MaterialMergeLog`, and deletes the losing catalog material in one transaction. The dialog claims the loser remains soft-deactivated with a `mergedIntoId` pointer and that rollback is available for 24 hours, but neither behavior exists in the catalog merge service or schema path reviewed here. The merge dialog can also be dismissed during execution, hiding completion or failure. Its notes field is hard-coded to an empty string. The page-level create/edit dialog success callbacks invalidate the same `listMaterials` query twice when `projectId` exists. This is redundant query invalidation rather than data corruption. The project editor is still labeled as an “Organization Custom Item” and “Save Changes” because its labels only distinguish global from non-global, even though the underlying update is correctly scoped to the project material ID.

Create and edit dialogs use the shared fuzzy-name picker, which debounces and queries up to six active matches. Suggestion rows are clickable `div` elements without keyboard roles or focus handling; nested “Select” and “Use” buttons offer a keyboard path, but row selection and menu navigation itself are not keyboard-operable. The create dialog has a `defaultRate` state value but no input for it, so every new material is submitted with rate zero. Create computes `normalizedName` from name plus specification; edit recomputes it from name alone, making the same record normalize differently after editing. Contractor should make match selection fully keyboard-operable and keep material identity normalization consistent across create, edit and import.

Contractor should expose project archive recovery, make destructive-operation progress and partial outcomes visible, and paginate or explicitly cap catalog registers.

The shared unit selector supports standard and custom units, and the common input's arithmetic behavior is conditional; the material create/edit fields do not enable arithmetic input. ## Organization rate-catalog governance route review

`/rate-catalogs` loads organization and global rate catalogs, then exposes Material Catalog, Rate Catalogs, Presets and Uncataloged Materials tabs. Selecting an organization rate catalog opens the shared `CatalogRatesLibrary` directly with `canWrite=true`; the route does not derive that flag from an explicit catalog edit grant. Catalog listing only verifies organization membership, while catalog mutations require organization inventory edit/admin, so the route can expose write controls to a member whose writes will be denied. The optional name in the global-catalog import dialog is never sent to `importFromParent`, and the dialog can be closed while its mutation is pending.

The Rate Catalogs tab also renders `CatalogRatesLibrary` with `canWrite=true`, no explicit scope and no project ID. It lists the scopes visible to the caller, then enables write controls regardless of the selected catalog's write grant. Its empty-catalog auto-sync therefore runs as soon as a catalog with no rates is selected, including for view-only callers whose mutation will fail. The create dialog falls back to `scope="project"` when no scope is passed, but the route supplies no `projectId`; creating a catalog from this organization screen is therefore configured as a project-scope request with a missing project identifier and is rejected by the server. This page should pass the organization scope and derive edit affordances from the catalog's authorization.

The uncataloged list endpoint defaults to 100 rows, and this page does not request a larger limit or paginate. Search filters only the loaded rows. “Scan Projects” and promotion/ignore actions are displayed without checking the user's edit grant; the server correctly enforces organization inventory edit and project materials edit, so view-only members see actions that fail when submitted. The scan creates or finds queue records but does not increment `occurrenceCount` for repeat discoveries, while the UI presents that field as the number of project uses.

Suggested matches span both global and organization catalogs. The row-level and promotion-dialog “Map to this” handlers always send `targetType: level` (`org` on this route), even when the selected suggestion is global; the server rejects the mismatched target scope. The server does support importing/adopting a global suggestion into the organization when `targetType: global` is passed, so the UI needs to preserve each suggestion's scope. The badge's stats error alert is rendered only after a successful response with a positive pending count; failures or an empty queue hide that error. Bulk promotion runs one mutation at a time and can partially succeed, but it clears selection and reports only the success count without naming failures. Bulk ignore swallows individual errors and reports the full selected count as ignored even if some requests failed.

The promotion server transitions each item with a compare-and-swap, checks organization/project permissions, and links matching project records within a transaction. The dialog itself prevents closing through Cancel while pending but does not pass the shared dialog `busy` prop, so Escape and backdrop dismissal can still hide the running operation. ## BOQ Excel import and paste review

The Excel file picker in the BOQ page accepts `.xlsx`, `.xls` and `.csv`, rejects files over 10 MB before parsing, then reads the `BOQ` sheet or falls back to the workbook's first sheet. It maps common code/description/unit/quantity/rate/category/section headings, strips formatting characters before numeric parsing, skips rows without code/description and `GRAND TOTAL`, then calls `boq.create` separately for each remaining row. The server requires BOQ edit permission and checks project lock and duplicate project/code, but each created row commits independently. The normal page's toolbar hides the paste entry when the user lacks BOQ edit access or the BOQ is locked, while `boq.create` remains the final server guard. Contractor should validate a complete import before writing, expose row-level errors and partial completion, and keep dialog state and progress clear until all row writes settle.
